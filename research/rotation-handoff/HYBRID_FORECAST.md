# Гібридна оцінка сівозмін на майбутні дати

`GET /api/rotations/forecast/catalog` повертає доступні ділянки, 13 профілів культур і приклади тривалості фаз. `POST /api/rotations/forecast` порівнює 2–3 плани з вибраними культурами для 1–3 спільних дат сівби. Для кожної дати можна встановити останню добу розрахунку. Старий маршрут `POST /api/rotations/assessment` доступний для порівняння двох готових планів на архівних сезонах.

## Як подати запит

Вибери `field_id` із каталогу. Для іншого поля передай об’єкт `field` з полями `id`, `name`, `latitude`, `longitude`. Сервіс підтягує за координатами п’ять шарів SoilGrids до метра. Якщо є власний профіль, передай обидва поля `soil_source_url` і `soil_layers`. Шари мають іти від поверхні без проміжків і покривати щонайменше 1 м. У кожному шарі передай `top_m`, `bottom_m` у метрах та `field_capacity`, `wilting_point` у м³/м³. [Приклад профілю ґрунту](examples/fields-to-add.json) · [SoilGrids WCS](https://docs.isric.org/globaldata/soilgrids/wcs.html)

У `seasons` передай дати сівби `planting_date` від сьогодні за UTC, у хронологічному порядку. Необов’язкове `through_date` обмежує сезон включно. Розрахунок має завершитися в межах трьох років від дати запиту. Кожен наступний сезон починається після завершення попереднього. Для кожного плану в `plans` постав культури в тому самому порядку, що й дати в `seasons`. Вибери календар через `calendar_id` із каталогу або передай `stage_lengths` з чотирма тривалостями в днях для початкової фази, розвитку, середини сезону й завершення. Для власного календаря тривалість усіх фаз разом має становити до 366 днів. Якщо профіль має календар за замовчуванням, можна передати тільки `crop_id`. [Профілі та календарі FAO‑56](https://www.fao.org/4/X0490E/x0490e0b.htm)

Замінюй дати прикладу на актуальні перед запуском.

```json
{
  "field_id": "marsden_demo",
  "seasons": [
    {"planting_date": "2027-05-01"},
    {"planting_date": "2028-05-01"}
  ],
  "plans": [
    {"id": "maize-then-sunflower", "crops": [{"crop_id": "maize_grain"}, {"crop_id": "sunflower"}]},
    {"id": "sunflower-then-maize", "crops": [{"crop_id": "sunflower"}, {"crop_id": "maize_grain"}]}
  ],
  "live_days": 7
}
```

Щоб перевірити змішаний режим, вкажи дату сівби в межах найближчого тижня. Якщо дата сівби пізніша за доступний горизонт актуального прогнозу, для цього сезону використовуються архівні сценарії з першого дня.

## Звідки беруться погода й стартова вода

- `live_days` задає від 1 до 10 днів від дати запиту за UTC. За замовчуванням це 7. Дні сезону, які потрапляють у цей проміжок, використовують актуальний прогноз Open‑Meteo. [Прогноз Open‑Meteo](https://open-meteo.com/en/docs)
- Для пізніших дат сервіс використовує до п’яти недавніх історичних сценаріїв. Для кожного знаходить відповідну календарну дату початку в попередньому році й відтворює доби послідовно. Після різниці у високосних днях дати можуть зміститися відносно календаря. Для сівби 29 лютого історична послідовність починається 29 лютого. Плани в одному сценарії отримують однакову погоду на спільних датах. [Архів Open‑Meteo](https://open-meteo.com/en/docs/historical-weather-api)
- Можна передати `initial_moisture` для конкретного сезону. Наприклад, `{"theta":[0.25,0.30,0.33],"source":"вимірювання в полі перед сівбою"}`. Три числа — об’ємна вологість у м³/м³ для шарів 0–7, 7–28 і 28–100 см. Команда може передати дані тіммейта, якщо має значення для всіх трьох шарів на початок сезону.
- Без явно переданої вологості кожен сценарій стартує зі значень архівної вологості за день до відповідної історичної дати сівби. Усередині сезону баланс продовжує облік запасу на межі прогнозного й архівного рядів. Кожен наступний сезон починається зі своєї стартової оцінки.
- Для завантаження погоди потрібен доступ до інтернету. Якщо потрібне джерело не відповідає або повертає неповний ряд, API повертає помилку.

### Дані з карти й джерела NASA

Для нового поля команда передає в `field.latitude` і `field.longitude` одну репрезентативну точку ділянки в десяткових градусах. API цього пакета приймає `field_id` для своїх каталогових ділянок. Ідентифікатор із карти основного застосунку потребує перетворення на координати під час інтеграції. За наявності узгоджених оцінок на початок сезону можна передати `seasons[].initial_moisture.theta` і `source`. Передавай три об’ємні частки у м³/м³ для 0–7, 7–28 і 28–100 см. Наприклад, 25% об’ємної вологості записується як `0.25`. Одне число з поверхневого шару, вологість у відсотках від польової вологоємності й індекс зеленості NDVI самі по собі не дають цих трьох значень. Для неповного профілю лишай `initial_moisture` порожнім. Тоді API бере архівний профіль і вказує джерело в `opening_source`.

Пакет отримує прогноз від Open‑Meteo, архівну погоду ERA5‑Seamless і стартові оцінки вологості ERA5‑Land. Добові поля погоди `rain_sum` і `et0_fao_evapotranspiration` вимірюються в міліметрах за добу, додатковий прогнозний `showers_sum` також у міліметрах за добу. `temperature_2m_min` і `temperature_2m_max` — у °C. Шари стартової вологості зчитуються з `soil_moisture_0_to_7cm_mean`, `soil_moisture_7_to_28cm_mean` і `soil_moisture_28_to_100cm_mean`. Це сіткові оцінки постачальника, точність яких для конкретного поля окремо не перевірено. [Прогноз Open‑Meteo](https://open-meteo.com/en/docs) · [Архів Open‑Meteo](https://open-meteo.com/en/docs/historical-weather-api)

В основному застосунку команда використовує ERA5‑Land для історичної вологості, ECMWF IFS для короткого прогнозу й Sentinel‑2 для зображень та NDVI. NASA SMAP є в окремому дослідницькому прототипі, а NASA POWER — у старішому прикладі Marsden основного застосунку. Жодне з цих джерел NASA не зчитується маршрутом гібридного прогнозу цього пакета. Результати дослідницьких тестів із синтетичними даними та поля із позначкою `null` не можна підписувати як польові вимірювання або нульові значення. [NASA SMAP](https://smap.jpl.nasa.gov/) · [NASA POWER Daily API](https://power.larc.nasa.gov/docs/services/api/temporal/daily/)

## Як показувати результат

`as_of` — дата розрахунку, `field_id` — вибрана ділянка, `weather` описує джерела й історичні сценарії. У `plans` є `members` із результатами кожного сценарію та `minimum_pct`, `median_pct`, `maximum_pct` за цією вибіркою. У кожному сезоні `weather_segments` показує дати й джерело погодного ряду. `opening_source` і `opening_historical_date` показують джерело й архівну дату стартової вологості. Якщо весь період вкладається в актуальний прогноз і передано стартову вологість, повертається один розрахунок із `interpretation: live_only`.

`water_shortfall_pct` показує частку розрахункової потреби у воді, яку не вдалося покрити. Якщо розрахункова потреба за цей період дорівнює нулю, поле має значення `null`. Показник `flowering_stress_days` належить до вікна цвітіння. Дати цвітіння доступні для профілів із підтриманими температурними порогами.

`water_stress_comparable` показує, чи є повна оцінка сумарного водного стресу для всіх планів. У кожному `plans[].members[]` є `crop_days` для загальної кількості днів росту, `drought_stress_days` для днів нестачі води, `waterlogging_stress_days` для днів перезволоження та `water_stress_days` для днів з одним чи обома типами стресу. Частка таких днів у сценарії — `water_stress_days_pct`. Медіана за всіма сценаріями плану — `plans[].median_water_stress_days_pct`. За відсутності оцінки перезволоження сумарні поля відповідного сценарію та медіана плану мають значення `null`.

Метод дефіциту позначено як `formula`. Польову похибку для цього гібридного режиму ще не оцінено. Сезонні результати після актуального горизонту описують історичні сценарії з однаковим прогнозним початком. Добовий баланс використовує рідкі опади й необов’язковий заданий полив. Сніготанення та промерзання ґрунту потребують окремого моделювання.

Тривалість фаз, глибина коріння й потреба у воді залежать від місцевого сорту та умов. Розрахунок обмежує глибину кореневої зони до 1 м, у каталозі це позначено в `root_depth_limited` для профілів, чия довідкова мінімальна глибина більша. [Глибини кореневої зони FAO‑56](https://www.fao.org/4/X0490E/x0490e0e.htm)

Після встановлення залежностей виконай `python check_hybrid_forecast.py` у середовищі пакета. Перевірка працює локально й охоплює перехід між джерелами погоди, продовження водного балансу та доступність усіх 13 профілів.

## Полив, вимоги до обладнання та пріоритети

У кожному плані можна передати `irrigation`, наприклад `[{"date":"2027-06-12","net_mm":20}]`. Це чиста кількість води, яка потрапляє в ґрунт, у міліметрах. Потрібен один запис на добу в межах сезону. Модель застосовує той самий графік в усіх погодних сценаріях цього плану. Порожній графік означає розрахунок без поливу. `irrigation_system` описує наявну систему, а графік і кількість води задаються окремо. [Стандарт управління поливом USDA NRCS](https://www.nrcs.usda.gov/resources/guides-and-instructions/irrigation-water-management-ac-449-conservation-practice-standard)

Каталог `GET /api/rotations/forecast/catalog` повертає `equipment[]` з ідентифікатором, назвою та призначенням для мультиселекту. Запиши вибране в `farmer.equipment_ids`, а доступ через підрядника можна передати у `farmer.equipment_access`. Якщо список ідентифікаторів передано, невибрана техніка з каталогу вважається недоступною, доки явний статус цього не змінить. Порожній список фіксує, що фермер нічого не вибрав.

Якщо план без `required_equipment` і фермер заповнив мультиселект, API підставляє базові припущення щодо сівби й збирання за культурою. У відповіді є `required_equipment` та `equipment_requirements_source`. Наприклад, для кукурудзи це просапна сівалка й зернозбиральний комбайн. Для графіка поливу з відомим типом системи також додається відповідна дощувальна або краплинна установка. `required_equipment` від інтеграції замінює базові припущення, наприклад коли господарство використовує інший спосіб сівби або має іншу жатку.

Статуси `owned` і `contracted` означають, що техніка доступна. `unavailable` блокує план. `unknown` або відсутність відомостей без мультиселекту потребують підтвердження. `required_equipment: []` явно задає план без вимог до обладнання. Якщо фермер позначає полив недоступним, план із графіком поливу отримує статус `infeasible`. Його розрахунок доступний як сценарій із заданими умовами.

У формі фермер обирає один пріоритет. Передай його в `farmer.priorities` як масив з одним значенням. Якщо поле пропустити або передати `[]`, API поверне порівняння без рейтингу. Доступність техніки й поливу визначає, які плани здійсненні. Серед них API присвоює `rank` за вибраним показником. Решта показників допомагають зрозуміти, що дає кожен план. За однакових значень плани ділять місце. Якщо хоча б одному здійсненному плану бракує зіставних даних, обраний критерій потрапляє до `decision.priorities_missing`, а місця залишаються порожніми.

Приклад для пріоритету «Менше води на полив» на майбутній сезон. Графік поливу й доступність обладнання тут умовні.

```json
{
  "field_id": "marsden_demo",
  "seasons": [{"planting_date": "2027-05-01"}],
  "farmer": {
    "equipment_ids": ["row_planter", "sprinkler"],
    "equipment_access": {"grain_combine": "contracted"},
    "irrigation_available": true,
    "irrigation_system": "sprinkler",
    "priorities": ["water_saving"]
  },
  "plans": [
    {
      "id": "maize-rainfed",
      "crops": [{"crop_id": "maize_grain"}]
    },
    {
      "id": "maize-irrigated",
      "crops": [{"crop_id": "maize_grain"}],
      "irrigation": [{"date": "2027-06-12", "net_mm": 20}]
    }
  ]
}
```

Для списку у формі використовуй `priorities` із `GET /api/rotations/forecast/catalog`.

| Назва у формі | Ключ API | Що порівнюємо |
|---|---|---|
| Менше днів водного стресу | `water_stress` | Меншу частку днів росту зі стресом від нестачі води або перезволоження. Порівнюємо медіани за погодними сценаріями. |
| Менше дефіциту води | `water_deficit` | Меншу частку незадоволеної потреби культури у воді. Порівнюємо медіани за погодними сценаріями. |
| Менше води на полив | `water_saving` | Меншу суму чистого поливу за графіком, мм. |
| Більше товарного врожаю | `yield` | Більшу суму заданої або довідкової товарної врожайності за всі повні сезони, т/га. |
| Вища виручка | `revenue` | Більшу виручку в однаковій валюті за всі повні сезони, до віднімання витрат. |
| Довше тримати ґрунт під живим покривом | `soil_cover` | Більше днів живого покриву в спільному періоді. Показуй цей варіант, коли відомі дати покриву для кожного плану. |

Для `water_stress` у кожному погодному сценарії зводимо дати водного стресу для кожної культури. Якщо в одну добу для культури позначено і нестачу води, і перезволоження, рахуємо її один раз. Далі ділимо суму днів стресу всіх культур на суму їхніх днів росту в цьому сценарії. Підсумкове число для рейтингу — медіана цих часток. Наприклад, 20 днів стресу на 160 днів росту дають 12,5% у сценарії. Вибір `water_stress` автоматично вмикає оцінку перезволоження. Якщо хоча б для одного плану немає повної оцінки перезволоження, API повертає `water_stress` у `decision.priorities_missing`, а місця залишає порожніми.

Для `water_deficit` у кожному сценарії ділимо суму дефіциту води в міліметрах на суму розрахованої потреби культур у воді. Наприклад, 60 мм дефіциту на 400 мм потреби дають 15%. Медіана за сценаріями доступна в `plans[].median_pct`. Для `yield` використовуємо `plans[].economics.marketable_yield_t_ha`. Це заданий або довідковий показник для всіх сезонів плану. Його можна показувати й поруч із рейтингом за іншими пріоритетами.

У формі `revenue` є єдиним фінансовим пріоритетом. Виручка дорівнює врожайності, помноженій на ціну продажу за тонну. Для демоточки Marsden API підставляє опубліковані орієнтири, якщо `economics` пропущено. У `crops[].economics` можна передати власні `marketable_yield_t_ha`, `farmgate_price_per_t`, `currency`, `source` і вологість товарного врожаю `yield_moisture_pct`. Витрати фермер може оцінити окремо. Для розрахунку довідкової маржі потрібне також `included_cost_per_ha`. Коли `through_date` обриває сезон, планові показники врожайності, виручки та маржі мають значення `null`. [Ціни виробників USDA](https://www.nass.usda.gov/Surveys/Guide_to_NASS_Surveys/Prices_Received_and_Prices_Received_Indexes/) · [Орієнтири витрат Айови](https://www.extension.iastate.edu/AGDM/crops/html/a1-20.html)

## Показники надлишку води й ґрунту

- `water_management` повертає полив і дренаж базового водного балансу. Щоб додати оцінку перезволоження, передай `"estimate_waterlogging": true` у прогнозному запиті або обери пріоритет `water_stress`. У кожному сезоні й погодному сценарії `water_management.waterlogging` повертає `days_above_field_capacity`, пікову об'ємну вологість на кінець доби, оцінений дренаж і надлишок води понад насичення. `waterlogging_stress_days` заповнюється, коли є сумісний поріг для культури. Дефіцит води продовжує обчислюватися за базовою моделлю.
- Для ґрунту в шарах 0–5, 5–15, 15–30, 30–60 і 60–100 см беремо середні значення SoilGrids `bdod` (об'ємна щільність, сг/см³), `clay` і `silt` (г/кг), `phh2o` (pH × 10), `cec` (ммоль заряду/кг), `wv0033` і `wv1500` (вода за 33 і 1500 кПа, 10⁻³ м³/м³). Об'ємну вологість насичення й насичену гідравлічну провідність оцінюємо рівняннями HiHydroSoil v2. Провідність перераховуємо із см/добу в мм/добу. Залишок води понад польову вологоємність після розрахованого дренажу переносимо на наступну добу. Такий баланс припускає вільний вертикальний дренаж через єдину кореневу зону. Ґрунтові води, затоплення від сусідніх ділянок і мережі дренажу потребують окремих даних. [SoilGrids](https://docs.isric.org/globaldata/soilgrids/SoilGrids_faqs_01.html) · [HiHydroSoil v2](https://www.futurewater.nl/wp-content/uploads/2020/10/HiHydroSoil-v2.0-High-Resolution-Soil-Maps-of-Global-Hydraulic-Properties_v2.pdf) · [Дренаж AquaCrop](https://www.fao.org/fileadmin/user_upload/faowater/docs/AquaCropV40Chapter3.pdf)
- Для дев'яти профілів беремо опубліковані `Aer` і `LagAer` із AquaCrop-OSPy. Для кукурудзи й соняшнику `Aer` дорівнює п'ятьом об'ємним відсотковим пунктам нижче насичення, `LagAer` задає три дні до повної сили ефекту за тривалого насичення. День з оцінкою обмеженої аерації враховує вологість і тривалість безперервного епізоду. Якщо поріг за даними двох джерел не вищий за польову вологоємність або для культури немає параметрів, API повертає пояснення в `crop_stress_status` та залишає дні стресу порожніми. Якщо шарів узагалі бракує, `waterlogging_soil_status` має значення `soil_data_unavailable`. За несумісного профілю кореневої зони `waterlogging_profile_incompatible` дорівнює `true`. Модель дає сценарну оцінку без польової перевірки, з однаковими параметрами по фазах. [Параметри культур](https://github.com/aquacropos/aquacrop/blob/256cac4c2cebd261818debd612c26f2eab561865/aquacrop/entities/crops/crop_params.py) · [Рівняння аерації](https://github.com/aquacropos/aquacrop/blob/256cac4c2cebd261818debd612c26f2eab561865/aquacrop/solution/aeration_stress.py#L50-L68)
- `soil.living_cover` приймає задані інтервали `[{start,end}]` включно. Дні перекриття рахуються один раз. Порожній список означає підтверджену відсутність живого покриву. Цей показник описує практику на полі. [Принципи ґрунтового здоров’я USDA NRCS](https://www.nrcs.usda.gov/conservation-basics/soil/soil-health/soil-health-on-cropland)
- `soil.erosion` приймає п’ять зіставних факторів `r`, `k`, `ls`, `c`, `p` та `source`. Їхній добуток у метричній системі дає орієнтовну середньорічну втрату ґрунту, який змивають дощ і поверхневий стік, у т/га/рік. На одному полі в `r`, `k`, `ls` закладають однакові умови опадів, ґрунту та схилу. Сівозміни відрізняються покривом і обробітком (`c`) та протиерозійними практиками (`p`). Наприклад, покривна культура закриває ґрунт після збирання, коли він інакше залишався б відкритим дощам. API бере `c` і `p` із запиту, а дні живого покриву рахує окремо. За наявності всіх факторів `soil.erosion_t_ha_year` можна показати довідково. [Метод RUSLE USDA](https://www.ars.usda.gov/midwest-area/west-lafayette-in/national-soil-erosion-research/docs/usle-database/research/)
- `soil.harvests` приймає врожай `yield_t_ha`, коефіцієнти винесення `p2o5_kg_per_t`, `k2o_kg_per_t` і `source` для кожного збирання. На виході сумарне винесення з урожаєм у кг/га. Узгодь вологість урожаю з джерелом коефіцієнтів. Для норм добрив і повного балансу потрібні також аналіз ґрунту та дані про надходження і втрати. [Довідник Iowa State PM1688](https://store.extension.iastate.edu/product/pm1688-pdf)

Для перевіреного профілю можна передати `waterlogging_soil` з полем `source` і масивом `layers`. Кожний шар містить `top_m`, `bottom_m`, `saturation` у м³/м³ і `saturated_conductivity_mm_day`. Шари мають безперервно покривати перший метр. Явний профіль має перевагу над підвантаженням SoilGrids. Використовуй узгоджені значення насичення, польової вологоємності й точки в’янення.

У [прикладі Marsden із SSURGO](examples/marsden-ssurgo-water-stress.json) обидва ґрунтові входи взято з одного компонента Nicollet (`cokey=28627779`, 85% картографічної одиниці `2834849`). З таблиці `chorizon` використано `hzdept_r`, `hzdepb_r` (см), `wthirdbar_r`, `wfifteenbar_r`, `wsatiated_r` (об’ємні %), `ksat_r` (мкм/с). Коефіцієнт провідності перераховано множенням на 86,4, останній шар обрізано до 1 м. Це репрезентативні значення ґрунтової карти, які команда може передати як альтернативний профіль. [Запит USDA Soil Data Access](https://sdmdataaccess.nrcs.usda.gov/Query.aspx) · [Опис колонок USDA](https://www.nrcs.usda.gov/sites/default/files/2022-08/SSURGO-Metadata-Table-Column-Descriptions-Report.pdf)

На архівній погоді 2021–2025 цей тестовий план дає сумісні пороги аерації для кукурудзи й соняшнику. За провідності з SSURGO та припущення вільного дренажу навіть повністю насичена коренева зона до кінця доби опускається нижче порога обмеженої аерації. Тому в кожному прикладі модель повертає нуль днів стресу від перезволоження. Цей результат описує припущення моделі. Для польової оцінки потрібні спостереження вологості або підтоплення й дані про ґрунтові води та дренаж.

Перевірка на архівній погоді Marsden. Модель оцінила для кукурудзи 16 днів понад польову вологоємність за погодою 2023 року і 52 дні за погодою 2024 року. Для соняшнику вийшло 14 і 42 дні. Для обох культур розрахований поріг нестачі повітря опинився нижче оціненої польової вологоємності, тому дні стресу залишено порожніми. Це порівняння сценаріїв із записаною погодою без незалежних польових вимірювань перезволоження.

Для оцінки зміни ґрунту між сезонами потрібен окремий розрахунок залишків, надходження й втрат поживних речовин. Живий покрив описує заявлену практику. Коефіцієнти RUSLE та винесення з урожаєм обчислюються за входами до запиту.

## Довідкові дані Marsden

`GET /api/rotations/forecast/references/marsden_demo` повертає джерела, вихідні одиниці, назви таблиць і колонок та перераховані значення з трьох файлів `marsden-*.json` у пакеті. Це зафіксовані дані з відомим роком та географією. Зовнішні сайти не потрібні під час підстановки цих значень.

- **Економіка.** Якщо для культури є опубліковані значення, API підставляє їх і позначає `input_origins: published_benchmark`. Довідкові бюджети не враховують землю, працю і доданий полив. Для сезону з графіком поливу умовна маржа лишається недоступною без повного бюджету для поливного варіанта. Урожайність і ціна лишаються опублікованими орієнтирами. За відсутності опублікованої ціни, урожайності чи витрат відповідні значення лишаються порожніми.
- **Винесення P₂O₅ і K₂O.** Iowa State PM 1688, таблиця 2, дає концентрації на одиницю товарного врожаю та стандартну вологість. Якщо `soil.harvests` пропущено, API використовує відомі коефіцієнти й урожайність, за потреби перераховану на вологість довідника. `crop_benchmarks` показує, що саме використано для кожного сезону. Сумарний результат за планом доступний, коли є дані для всіх його культур. Явний `soil.harvests` має пріоритет. [Таблиця Iowa State](https://store.extension.iastate.edu/product/pm1688-pdf)
- **Водна ерозія.** Для демоточки API має `R` із растра GloRESatE і `K` та `LS` на основі ґрунтової карти SSURGO. Для власного плану залишаються потрібні `soil.erosion_management.c`, `p` і `source`. У `erosion_inputs_missing` видно, чого бракує. Польова стаття Hunt та співавторів, таблиця 4, подає історичні змодельовані показники ерозії й втрат поживних речовин для дослідних ротацій. Ці оцінки доступні як контекст і не підставляються замість оцінки власного плану. [Растр GloRESatE](https://zenodo.org/records/11078865) · [SSURGO](https://www.nrcs.usda.gov/resources/data-and-reports/soil-survey-geographic-database-ssurgo) · [Дослідження Marsden](https://pubs.acs.org/doi/10.1021/acs.est.8b02193)
- **Історичні аналізи ґрунту.** `mrs_nutrients18.csv` має колонки `date`, `plot_id`, `depth_cm`, `msmt`, `value` та ідентифікатори року й дня. `tidy-soilN-marsden.csv` має дати, ділянки, шари й окремі концентрації нітрату та амонію. Аналізи 2018 року описують ґрунт на час досліду. У прогнозі їх не підставляємо як сучасну родючість чи норму добрив. [Лабораторні аналізи Marsden](https://github.com/vanichols/maRsden/tree/master/data-raw/soil_tests) · [Дані мінерального азоту](https://github.com/vanichols/maRsden/tree/master/data-raw/soiln)

Довідкові врожайність, ціна і витрати наразі задаються по культурі. Якщо поміняти місцями ті самі культури, суми довідкової виручки, маржі та винесення лишаться однаковими. Водний баланс може відрізнятися через погоду відповідних років.

## Довідкові дані для інших країн

Приклад поля у Вінницькій області. Дату сівби можна замінити на актуальну. Інтернет потрібен для ґрунту й погоди.

```json
{
  "field": {
    "id": "vinnytsia_demo",
    "name": "Приклад Вінницької області",
    "latitude": 49.18,
    "longitude": 28.62
  },
  "seasons": [{"planting_date": "2027-05-01"}],
  "farmer": {
    "equipment_ids": ["row_planter", "grain_combine"],
    "irrigation_available": false,
    "priorities": ["revenue"]
  },
  "plans": [
    {"id": "maize", "crops": [{"crop_id": "maize_grain"}]},
    {"id": "sunflower", "crops": [{"crop_id": "sunflower"}]}
  ]
}
```

- **Країна.** Код `country_code` визначається за відкритими межами Natural Earth масштабу 1:50 млн. Для прикордонних та інших неоднозначних точок можна явно передати `country_code`, наприклад `UKR`, `DEU`, `BRA`. Код вибирає статистичну територію. [Межі Natural Earth](https://www.naturalearthdata.com/downloads/50m-cultural-vectors/50m-admin-0-countries-2/)
- **Ґрунт і погода.** Погода Open‑Meteo та гідравлічні властивості SoilGrids залежать від координат. Ґрунтові колонки `wv0033` і `wv1500` за п’ятьма шарами дають оцінену вологоємність і точку в’янення. За відсутності профілю від провайдера можна передати власні шари або отримати явну помилку.
- **Врожайність і ціна.** Вбудований зріз FAOSTAT має принаймні один показник у 183 країнах і територіях, 1 345 пар місце–профіль, з яких 815 мають обидва показники. З QCL береться `Yield` і перераховується за `Unit` у т/га. З PP береться `Producer Price (USD/tonne)`. Ключові колонки `Area Code (M49)`, `Item Code (CPC)`, `Element`, `Year`, `Unit`, `Value`, `Flag`, а в PP ще `Months = Annual value`. Показники є медіанами до трьох останніх спільних наявних років від 2021-го. Якщо є лише один показник, він зберігається окремо. Роки й початкові значення повертає `GET /api/rotations/forecast/countries/{country_code}`. Це національні орієнтири, а в довіднику пшениці трапляється спільний показник для її форм. [Урожайність FAOSTAT](https://data.fao.org/catalog/iso/d24a448b-3b62-4c09-8c1d-4a39bb599876) · [Ціни виробників FAOSTAT](https://data.fao.org/catalog/dataset/47c17894-8ca1-4bd0-ba4d-6078e919e9b1)
- **Виручка й маржа.** `gross_revenue_per_ha` — врожайність × ціна за повні сезони, коли для всіх культур є обидва значення. `gross_margin_per_ha` потребує зіставних витрат. За межами демоточки Marsden у пакеті немає підключеного джерела витрат. Для рейтингу за виручкою є окремий пріоритет `revenue`. Для власних оцінок можна передати `economics`.
- **Винесення з урожаєм.** У країнах з наявною врожайністю беремо коефіцієнти FAOSTAT Cropland Nutrient Balance, таблиця 4. Оригінальні колонки — код культури та кг елементарного P і K на тонну зібраного продукту. Перераховуємо в еквіваленти P₂O₅ і K₂O. Ці коефіцієнти застосовуємо до сумісної врожайності з FAOSTAT. Для власної врожайності можна передати `soil.harvests` із відповідними коефіцієнтами. [Методика FAOSTAT, таблиця 4](https://files-faostat.fao.org/production/ESB/ESB_e.pdf#page=7)
- **Ерозія.** `rainfall_erosivity_r` підтягується за координатами з історичної глобальної сітки GloRESatE v2 з кроком 0,1°, де є значення. `"estimate_erosion_erodibility": true` окремо підтягує середні `sand`, `silt`, `clay` (г/кг) та `soc` (дг/кг) для шару 0–5 см із SoilGrids і рахує метричний `soil_erodibility_k` методом EPIC. Для схилу передай `ls` або пару `slope_percent` і `slope_length_m` у `soil.erosion_management`. Довжина означає горизонтальний шлях поверхневого стоку на однорідному схилі. Для кожного плану передай `c` для покриву й обробітку, `p` для захисних практик та `source`. За наявності всіх факторів `soil.erosion_t_ha_year` показує довгострокову середньорічну оцінку змиву ґрунту. Для окремого дощу ця формула оцінки не дає. Поле `erosion_inputs_missing` перелічує відсутні фактори. [GloRESatE v2](https://zenodo.org/records/11078865) · [EPIC K](https://storage.googleapis.com/releases.naturalcapitalproject.org/invest-userguide/latest/en/sdr.html#soil-erodibility-k) · [USDA RUSLE](https://www.nrcs.usda.gov/resources/tech-tools/water-erosion-rusle2)
