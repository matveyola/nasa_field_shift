# Стан проєкту

## Поточна готовність — 2026-11-14

У репозиторії є повний склад застосунку: API, web, приватний асистент і widget, ML-пакет, усі десять міграцій БД, тести, ресурси, Compose, резервне копіювання та CI/release workflows. Локальний Docker-стек з agent profile запущений і доступний на http://localhost:8080. Готовність компонентів і результати перевірок наведені нижче.

Загалом у перелічених suites успішно виконано **1189 тестів**: 1188 із компонентних suites та новий регресійний тест build topology. Повторний запуск тих самих п’яти Docker-інтеграційних тестів не додається до цього числа. Пропуски не зараховано як успішні результати. Окремі smoke-перевірки не додаються до цього числа.

### Межі перевірки

- Опційні embeddings і dense/reranker моделі не встановлювалися; дороге навчання не запускалося.
- Живий OpenAI-сумісний провайдер перевірено одним коротким запитом; це не повний eval моделей. Gemini й Anthropic не викликалися. Налаштування провайдерів описані в [інтеграції асистента](assistant-integration.md).
- Unit-запуски можуть повідомляти про deprecation у залежностях; web/widget build попереджає про великі chunks.
- Оцінка production-готовності й комерційних умов джерел даних залишається окремою роботою.

Перед залежними задачами відповідні зміни мають бути вже в персональній гілці: #2 → #3–#6 → #7.

Окремі 10 тестів механізму інтеграції на тимчасових локальних Git-репозиторіях перевірили успішну публікацію, повторний запуск, конфлікти, падіння перевірок, зміну дерева перевірками, блокування конкурентного агента, незбережену роботу, неопубліковані коміти та оновлення remote. Вони не входять у наведені вище 1189 тестів застосунку. Код застосунку не змінювався; його suites для цієї зміни повторно не запускалися.

### Агентне дерево та виконувані перевірки

Додано [систему агентів розробки](agent-tree.md): `task_lead`, `implementer`, `researcher`, `verifier`, `test_runner`, `integrator`. Конфігурація запитує до восьми дочірніх потоків; фактичні ліміти сесії мають пріоритет. Інструкції задають окремі worktrees для паралельних виконавців, незалежне приймання зафіксованого стану, спільний бюджет слотів і послідовну інтеграцію через наявне блокування.

`python3 infra/verify.py --mode tooling` пройшов: конфігурація, склад ролей, локальні посилання та 17 тестів інструментів. Ruff і форматування чотирьох Python-файлів перевірено з конфігурацією API. Валідатор навички та strict startup конфігурації Codex CLI 0.169.0 пройдено. Окремий smoke-сценарій реально виконав дерево корінь → керівник → дочірній тестувальник; сценарії зміни untracked-файла після рев'ю та пропуску обов'язкової інтеграції правильно визначено як блокуючі. Автоматичний вибір нових іменованих ролей у новій сесії ще не перевірено.

Runner `--mode fast --build` задає 18 послідовних команд із перевіркою контрактів перед споживачами та зупинкою на першому збої. Спроба запуску зупинилася на першій команді з кодом 127: `npm` недоступний у поточному середовищі. Application suites, Docker, інтеграційні й browser-тести для цієї зміни не виконувалися; попередні результати вище не є повторною перевіркою. Нові 17 тестів не входять до попереднього числа 1189.

До CI додано `Development agent checks` як залежність `Required checks`; YAML і залежність перевірено локально, GitHub workflow ще не запускався. Branch protection не змінювався. Код застосунку й dependency locks не змінено. Налаштування агентів потребує нової сесії в довіреному репозиторії; інструкції ролей не створюють окремих sandbox і не замінюють CI.

### Виправлення збірки спільного образу API

`build` у спільному Compose anchor створював кілька паралельних exporters для `field-shift-api:local`. На Docker 29 / BuildKit це відтворило помилку `image already exists`. Визначення `build` тепер належить лише сервісу `api`; migrate, dispatcher, refresh і workers використовують той самий готовий образ. Регресійний тест перевіряє унікальність image tags у реальному Compose build plan, падає на попередній конфігурації та проходить після виправлення.
