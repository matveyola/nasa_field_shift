# Planning workspace — issue #6 handoff

The exported workspace supports field-profile editing, a three-season farm plan,
scenario comparison, evidence inspection, explicit apply, and replan differences.
It uses the frozen planning-v1 DTOs from issue #2 (`ebefa04`). It is intentionally
not registered in App/Shell/routing: shared navigation and live wiring belong to #7.

## Mounting

Import `PlanningWorkspace` and `PlanningWorkspaceProps` from
`apps/web/src/features/planning`. Its CSS is imported by the component and scoped
to the workspace. Keep the existing shared theme and fonts. Both Ukrainian and
English labels live in `features/planning/i18n.ts`; no global locale edits are needed.

The integration owner supplies:

- `initialRequest`: an authenticated, versioned `FarmPlanningRequest`, including
  actual field snapshots, a weather scenario set and current commitments.
- `cropOptions`: available crop/cultivar references, not automatically supported
  models. Selecting Rice is not a claim of paddy-model availability.
- `context` / `onContextChange`: the shared selected field, harvest season and
  trajectory ID. Map existing app scenario IDs to actual available trajectories;
  do not equate arbitrary weather members with a global dry/wet label.
- `locale`: the existing app language (`uk` / `en`). Default is Ukrainian.
- Optionally `initialRun` and `currentProfiles`: load an existing run and monitor
  current revisions. A changed profile/geometry/snapshot or expired forecast
  disables applying the archived report.
- `onProfileSaved`: refresh the parent's profile/weather state after a save.
  A newly versioned profile needs weather traces tied to its new snapshot before
  another calculation. The client never relabels old traces as new source data.
- `loadEvidence(run, signal)`: resolve the immutable candidate/evaluation IDs from
  the run through A/B/C's owning adapters. The frozen contract defines these DTOs
  but no public retrieval endpoint. #7 must supply this port; this lane does not
  invent an endpoint or silently generate model results. Missing evidence is
  visibly unavailable, while saved plan reasons remain inspectable.

An optional `api` port supports deterministic tests or an integration adapter.
Production defaults to `createPlanningApi()` with the shared API base, session
and CSRF headers, plus planning-specific error decoding. There is **no production mock fallback**. A failed source
request cannot turn into a successful demo prediction.

Example mount (parent owns bootstrap, selection and access):

```tsx
<PlanningWorkspace
  initialRequest={planningInput}
  initialRun={savedRun}
  currentProfiles={latestProfiles}
  cropOptions={cropCatalog}
  context={{ fieldId: selectedFieldId, season, trajectoryId }}
  onContextChange={next => updateSharedPlanningContext(next)}
  locale={language}
  loadEvidence={loadSavedPlanningEvidence}
  onProfileSaved={refreshPlanningInputs}
/>
```

Switching farm remounts the session and aborts outstanding work. To explicitly
replace the whole draft/bootstrap session, the parent can additionally set a
React key to its own bootstrap revision. Do not repeatedly remount while a user
is editing. Current revision props can change without destroying the draft.

## User workflow

1. **Field and data quality.** Choose a field, season and scenario using shared
   selection callbacks. Field cards show area, profile/geometry revisions,
   issue time, weather grid/native resolution, source kind, coverage and
   attribution. Latitude, hemisphere, slope/aspect and UTC solar time stay
   distinct from modeled yield. No location-based suitability rule is invented.
2. **Profile.** Edit current crop/cultivar, dated crop history, completeness,
   soil horizons/texture/water limits, irrigation and management. Empty numeric
   inputs stay null; zero remains a valid value. Geometry and farm/field IDs are
   immutable in this editor. Changes add a `user_entered` source with SHA-256 of
   the edited inputs and source references on edited rows. They are not presented
   as fresh lab measurements. Save uses expected revision and a versioned profile;
   the owning API must enforce access, CAS and authoritative snapshot identity.
3. **Plan.** Select fields/crops, a three-season horizon, reference-margin,
   worst-tested-margin or water-demand goal. Configure per-season budget/currency,
   irrigation volumes, crop area/share limits, dated equipment capacity and
   crop commitments. Existing commitments cannot be removed by the form.
4. **Economics.** Enter price, variable costs excluding irrigation, separate irrigation costs, currency/date,
   provenance and harvest moisture basis for each crop/season/trajectory.
   Optional entered yields remain labeled assumptions. Blank economic values
   are not converted to zero or generated by an LLM. Required values and
   cross-field scope are checked before submission; domain feasibility stays in C.
5. **Save and calculate.** POST creates a durable run through C's API. Pending,
   running, failed, cancelled, infeasible, search-limit and empty results have
   different states. A bounded foreground poll uses 2.5-second intervals for at
   most 60 reads, pauses in hidden tabs and retains a manual refresh control.
   Network failures show an error instead of replacing results. Submit/replan
   retries retain the same request identity while the payload is unchanged.
6. **Compare.** Distinct alternatives use the same per-field/season/scenario
   yield, stress and irrigation displays, plus farm seasonal gross margins and
   worst tested total. The worst total is unavailable if any required trajectory,
   season, amount or currency is missing. There is no expected-profit/CVaR label
   for uncalibrated scenario weights. A single alternative is not duplicated.
7. **Inspect.** Matrix cells support arrow-key focus navigation and Enter/Space
   selection. The evidence panel shows crop/cultivar/rule/model versions,
   rejected/unchecked rules and saved evidence references. Values, uncertainty
   intervals and units are rendered directly; surface m³/m³ remains separate
   from root-zone mm and both preserve depths. It is a deterministic explanation
   of saved evidence, not a second model or an LLM inventing numbers.
8. **Apply.** Open the native modal dialog, review the assignments/commitments,
   check explicit human confirmation and submit. The request carries the saved
   input hash and expected profile/geometry revisions. Dirty inputs, stale reports
   and non-feasible jobs cannot be applied. Failed/stale/forbidden apply never
   displays success; only an applied/already-applied response with a timestamp
   acknowledges success. Retrying the same application retains its idempotency ID.
9. **Replan.** New calculation creates another run with commitment references;
   the previous alternative remains available for a field/season assignment diff,
   including cultivar changes. Existing crop history is not rewritten by a plan.

## API and failure boundaries

`apps/web/src/api/planningV1.ts` implements the reserved `/api/planning-v1/farms/...`
profile, run/list/detail, apply and replan routes. Calls use the shared API base,
session expiry behavior and CSRF headers; route IDs are URL-encoded. The planning
transport preserves C's structured `PlanningError` bodies, showing a plain state
message and the server's evidence references. Malformed/absent error bodies produce
an unavailable/conflict/access/input error, never replacement results. Responses
are structurally validated against the frozen JSON Schema with the existing Ajv
dependency. Farm, field, run and request identities are checked on the response.
The client is not an authorization boundary: A/C must still check access, current
versions, scientific applicability and all server-side semantic validators.

The current list contract is a bounded array. Cursor pagination or large-input
reference submissions require an agreed contract extension rather than a private
UI/server fork. The error details remain available for diagnostics; the form
shows a plain validation/incompatible-response message.

Public code never imports `tests/planning` or `e2e/planning-v1`. The isolated
harness explicitly imports synthetic fixtures and always shows the synthetic
data banner. No training, live weather API, paid LLM or GPU execution is required.

Browser cases read the immutable G01–G24 manifest. They exercise **presentation of
typed mocked statuses/results**, including Antarctica evidence vs missing data,
northern summer/winter, bounded irrigation, rice vs hazardous inundation,
unknown hybrids, soil fertility under drought, ocean and future/unavailable inputs.
They do not execute the future agronomic models or certify geographical accuracy.
Model/domain predicate execution remains in A/B/C and #7's release protocol.
