# План роботи

## Мета

Field Shift об’єднує карту полів, стан рослинності, водний баланс і планування культур. Кожна функціональна зміна має зрозумілу межу, релевантні перевірки та визначений спосіб відкату. Поточні результати перевірок наведені в [статусі](status.md), продуктові вимоги — у [баченні](vision.md).

## Межі комітів

Об’єднувати пов’язану поведінку, контракти, тести й залежності в один змістовний коміт. Не дробити одну функцію за назвами файлів. Окремо оформлювати незалежні функції, інфраструктурні зміни та підтверджені виправлення. На проміжному кроці можуть бути ще не підключені компоненти; готовність інтегрованого застосунку визначається перевірками, а не самою наявністю файлів.

Заголовок коміту називає конкретну зміну. Тіло пояснює поведінку, спосіб реалізації, мету, виконані перевірки та обмеження. Дата й автор відповідають фактичному коміту. Fix-коміт містить відтворювану проблему, причину й регресійну перевірку. Навчальні сценарії збоїв явно позначаються як вправи.

## Перевірки та приймання

Встановлювати залежності за lock-файлами. Починати з перевірок зміненого шару, потім виконувати відповідні компонентні та інтеграційні suites. Не запускати дороге навчання чи платні provider calls без потреби. Недоступний інструмент, сервіс або пропущений сценарій зазначається як обмеження, а не успішний результат.

Перед експлуатацією окремо підтвердити Docker-збірки, версії PostgreSQL/Redis, відновлення даних, права доступу, налаштування секретів і комерційні умови джерел. Актуальні пройдені та невиконані перевірки наведені в [статусі](status.md).

## Відкат

Перед відкатом зберегти незакомічену роботу. Переглянути `git log --oneline` і `git show <commit>`. Використовувати `git revert <commit>`; залежні зміни відкочувати у зворотному порядку. Для огляду попереднього стану використовувати окремий worktree. Не переписувати опубліковану історію та не застосовувати `reset --hard`.

Git не відкочує базу, зовнішні результати чи секрети. Перед зміною схеми потрібна резервна копія. Відновлювати її в нову БД, перевірити результат і лише потім перемикати застосунок. Відкат коду сам по собі не гарантує сумісності схеми.


## Planning integration and next acceptance gate

#3–#6 share the frozen planning-v1 base and are integrated through #7 into
`nazar-jobs`. The next scientific checkpoint is a permissioned pilot dataset,
reviewed regional rules, sealed holdouts and a reproducible independent
field/year evaluation. The current crop runtime abstains on mixed rotations and
unsupported management/cultivars. Do not describe technical integration or
synthetic geographic tests as measured recommendation accuracy. See
[operating limits](planning/runtime.md) and [data audit](planning/data-audit.md).
