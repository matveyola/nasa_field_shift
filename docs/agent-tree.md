# Агентне дерево для розробки Field Shift

Кореневий агент координує вимоги, залежності та спільні файли. Для незалежних напрямів він створює керівників задач, а кожен керівник організовує виконання й перевірку. Для невеликої задачі проміжний керівник не потрібний.

```text
Координатор
├── task_lead: API
│   ├── researcher — дослідження за потреби
│   ├── implementer — код і тести
│   ├── test_runner — виконання перевірок
│   └── verifier — незалежне приймання
├── task_lead: Web
│   └── така сама послідовність виконання й перевірок
└── integrator — послідовне злиття та перевірка спільного дерева
```

Це логічна структура: всі вузли не зобов'язані працювати одночасно. Після змін виконавця тестувальник і верифікатор працюють з одним зафіксованим станом. Верифікатор читає вимоги й код незалежно від висновків автора та враховує звіт тестувальника. Нові зміни потребують актуалізації відповідних перевірок. Дослідник і верифікатор завершують гілку без нескінченного створення наступних перевіряльників.

## Налаштування та запуск

[Конфігурація](../.codex/config.toml) вмикає субагентів і задає до восьми одночасних дочірніх потоків; моделі, reasoning і дозволи успадковуються від сесії. [Файли ролей](../.codex/agents/) визначають шість спеціалізацій. [Навичка agent-tree](../.agents/skills/agent-tree/SKILL.md) задає делегування, передачу результатів і приймання; [матриця перевірок](../.agents/skills/agent-tree/references/test-matrix.md) описує команди проєкту.

Відкрий нову сесію Codex у довіреному репозиторії після встановлення файлів. Налаштування проєкту можуть не застосовуватися в недовіреному каталозі; активна сесія може зберігати попередні ролі й обмеження. Фактичні можливості інструментів і політики середовища мають пріоритет над числом у конфігурації. У сесії, де доступно лише чотири агенти разом із кореневим, дерево працює етапами.

Приклади запитів:

```text
Використай $agent-tree для цієї задачі. Розділи незалежні API та Web роботи,
для кожного результату признач незалежного verifier і test_runner.
Інтегруй лише після перевірок спільного дерева.

Запусти test_runner у режимі full. Перевір усі локальні suites,
окремо покажи пропущені, недоступні та opt-in перевірки.

Виконай issues #3–#6 через агентне дерево після наявності #2 у nazar-jobs.
Використай issue-worktree для ізоляції та послідовної інтеграції.
```

Якщо інструмент створення агента не має параметра вибору ролі, координатор передає інструкції відповідного TOML у завданні дочірньому агенту. Назва потоку сама собою не активує роль. Без доступного spawning незалежна агентна перевірка позначається як невиконана.

## Паралельність і перевірки

Кореневий агент розподіляє єдиний бюджет слотів. Керівники можуть створювати вкладені підзадачі в межах трьох рівнів нижче кореня; це правило робочого процесу. За нестачі слотів завершують поточну роботу й використовують агентів повторно. Вісім слотів не означають по вісім на кожну гілку.

Кожен одночасний виконавець має власний worktree. Перевірки виконуються після зупинки записів у нього. Для незакомічених змін потрібні HEAD, перелік змін і хеші файлів, включно з новими файлами; одного SHA коміту недостатньо. Тимчасові звіти й журнали залишаються поза вихідним деревом.

`test_runner` має режими `affected`, `fast` і `full`. Повний режим враховує також пакет `field-shift-models`, який наразі відсутній у CI, інтеграційні й детерміновані browser-тести. Пропущена через відсутні сервіси обов'язкова перевірка блокує приймання навіть за exit code 0. Платні провайдери, опційні моделі й дороге навчання зазначаються окремо.

Інтеграційні тести використовують окремі PostgreSQL/Redis ресурси. Browser-тести потребують перевірки належності сервера: поточний Playwright може повторно використати порт 5173 іншого checkout. Docker-проєкти, порти, volumes та image tags також потребують ізоляції.

Для GitHub issues інтегратор використовує наявний [issue-worktree](../.agents/skills/issue-worktree/SKILL.md) і його спільне блокування merge → перевірки → push до персональної jobs-гілки. Звичайна задача сама собою не дозволяє push. Спільні контракти перевіряються повторно на об'єднаному дереві.

## Детерміновані перевірки

```bash
python3 infra/verify.py --mode tooling
python3 infra/verify.py --mode fast --build --list
python3 infra/verify.py --mode fast --build
```

[Виконуваний runner](../infra/verify.py) спочатку перевіряє актуальність валідаторів і типи контрактів, далі запускає збірки, перевірку типів, Ruff і unit-тести. Він зупиняється на першій помилці та повертає ненульовий код; залежності мають бути підготовлені за lock-файлами. `--list` лише показує план. Інтеграційні та browser-тести залишаються окремими кроками повного режиму агента.

[Валідатор налаштування](../infra/check_agent_tree.py) перевіряє TOML, склад ролей, бюджет, обов'язкові інструкції та локальні посилання. CI запускає його, тести інструментів і Ruff у job `Development agent checks`, який входить до залежностей `Required checks`. Обов'язковість цього статусу для merge визначає налаштування GitHub branch protection; цей запит його не змінює.

У цьому проєкті немає спільного ESLint-пакета чи `packages/contracts`. Не додаємо вигаданих команд до workflow: використовуємо наявні Ruff, TypeScript і перевірку згенерованих валідаторів. Нові правила імпортів потребують окремо визначених дозволених меж. Контрактні зміни спочатку узгоджують схеми та похідні артефакти в `services/agent/contracts`, після чого наступний агент отримує короткий пакет із контрактом, ревізією й критеріями приймання.

## Межі гарантій

Це конфігурація Codex та інструкції агентам, а не окремий сервер оркестрації. Вони не забезпечують програмно примусове дотримання кожного етапу: фактичними механізмами залишаються дозволи середовища, CI і блокування інтеграції. Read-only поведінка дослідника й верифікатора задана інструкціями; окремий sandbox для цих ролей не створюється.

Формат звірено з Codex CLI 0.169.0 та офіційною документацією [субагентів](https://learn.chatgpt.com/docs/agent-configuration/subagents) і [конфігурації](https://learn.chatgpt.com/docs/config-file/config-reference). Поточні результати перевірки цього налаштування наведено в [статусі](status.md).
